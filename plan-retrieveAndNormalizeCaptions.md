## Plan: Retrieve And Normalize Captions

TL;DR: Evolve the existing passive `GET_CAPTION_DIAGNOSTICS` probe into a two-stage, user-triggered caption workflow. The content script remains responsible for page inspection and candidate discovery; the service worker becomes the controlled retrieval broker; pure shared parsers normalize WebVTT, TTML, SRT, and provider JSON into a canonical cue document. Preserve the exact raw provider payload and a normalized export, with provenance and uncertainty attached to every candidate and cue. Keep the migration narrow by retaining the existing diagnostic collector as the discovery foundation and adding retrieval alongside it before removing disposable UI/schema pieces.

**Current baseline and hypothesis**
- `src/shared/messages.ts` defines `GET_CAPTION_DIAGNOSTICS` and a diagnostic-only response containing native tracks, evidence, and limitations.
- `src/shared/utils/caption-diagnostics.ts` only observes exposed `TextTrack` objects, nearby caption-like DOM, and page controls. It does not read response bodies, inspect resource timing, parse provider configuration, or retrieve files.
- `src/entries/content-script/index.ts` owns the page-side video map and same-origin iframe traversal. `handleGetCaptionDiagnostics` calls the collector directly; the popup bypasses the service worker with `chrome.tabs.sendMessage`.
- `src/entries/popup/App.tsx` owns the `Probe captions` button and downloads a JSON diagnostic report. It has no retrieval progress, candidate selection, raw/normalized download, or parse-error UI.
- `src/entries/background/service-worker.ts` forwards unknown tab-scoped messages but has no explicit caption retrieval/discovery case. It is the right owner for controlled extension-origin fetches, response limits, and cross-context orchestration.
- `src/manifest.json` already has `<all_urls>`, `activeTab`, `tabs`, `scripting`, and `downloads`. The likely first implementation needs no new permission, but must verify whether cross-origin authenticated fetches require an explicit host-permission or cookie policy change.
- Cheapest discriminating check during implementation: a fixture page with one native WebVTT track, one discoverable caption URL, and one malformed/unsupported candidate should produce a discovery response, a successful raw fetch, one canonical cue set, and an explicit parse/auth failure without blocking the other candidate.

**Recommended architecture and data model**
1. Split the workflow into discovery and retrieval/normalization. Discovery is page-local and fast; retrieval is an explicit user action and can be asynchronous.
2. Add a versioned canonical JSON document as the common internal/export format. Recommended shape:
   - document metadata: `schemaVersion`, `documentId`, `language`, `languageConfidence`, `title`, `duration`, `capturedAt`, and `normalizationWarnings`;
   - `cues`: stable `id`, `start`, `end`, `text`, optional structured `spans`/`settings`, optional `speaker`, optional `voice`, optional `language`, and cue-level `confidence`;
   - `styles`: optional named style records with foreground/background/color/font/position/alignment information where the source exposes it;
   - `source`: `kind` (`native-track`, `resource-url`, `provider-data`, `dom-sample`, `manual`), canonical URL when safe, page URL/origin, provider label, retrieval time, response content type, source format, request mode, and authentication status;
   - `uncertainty`: confidence, exact-vs-sampled timing, inferred fields, omitted features, parser warnings, and inaccessible/DRM/CORS limitations.
3. Preserve source data separately from the normalized representation. A result should contain candidate metadata, an exact raw payload download (or a clearly reported inability to obtain it), and the normalized canonical JSON. Do not silently rewrite raw bytes or claim that a DOM sample has exact cue boundaries.
4. Treat WebVTT, TTML/DFXP, SRT, and JSON as input formats, not as the canonical interchange. WebVTT and TTML retain different styling/positioning semantics; SRT loses styling; provider JSON varies widely. Emit optional WebVTT/SRT/TTML only as derived exports after canonicalization, with warnings for lossy conversion.
5. Keep parsing and normalization pure and testable. Do not parse untrusted caption text with `innerHTML`; represent text/spans as data and escape on export/render. Cap document size, cue count, cue text length, and recursion depth.

**Phased implementation**

### Phase 1: Establish contracts and preserve the existing diagnostic behavior
1. Extend `src/shared/messages.ts` near `ContentScriptMessage`, `PopupMessage`, `MessageResponse`, and the current caption interfaces with versioned discovery/retrieval types. Prefer distinct messages such as `DISCOVER_CAPTION_SOURCES`, `RETRIEVE_CAPTION_SOURCE`, and optionally `CANCEL_CAPTION_RETRIEVAL` over overloading `GET_CAPTION_DIAGNOSTICS`.
2. Define serializable types for `CaptionSourceCandidate`, `CaptionDiscoveryResponse`, `CaptionRetrievalRequest`, `CaptionRetrievalResponse`, `RawCaptionArtifact`, `NormalizedCaptionDocument`, `CaptionCue`, `CaptionSpan`, `CaptionStyle`, `CaptionProvenance`, `CaptionUncertainty`, parser warnings, and failure categories (`unsupported-format`, `network`, `cors`, `auth`, `size-limit`, `timeout`, `invalid-payload`, `inaccessible`). Keep the current diagnostic types temporarily so the migration can be incremental.
3. Give every candidate and retrieval result a stable ID, source kind, URL/reference, language/label, confidence, and evidence list. Make URL and provider metadata redaction-aware; do not expose signed query tokens in UI text or logs by default.
4. Decide whether discovery response is one snapshot or streamed progress. Recommend one bounded snapshot followed by per-source retrieval requests because popup lifetime is short and existing messages are one-shot.

### Phase 2: Expand page-side discovery with conservative evidence
1. Refactor `src/shared/utils/caption-diagnostics.ts` around the existing `collectCaptionDiagnostics`/`collectTracks`/`collectPageEvidence` helpers, or extract a new `src/shared/utils/caption-discovery.ts` while preserving the diagnostic output adapter.
2. Keep native track discovery first. Read `video.textTracks` and each child `<track>` independently instead of assuming equal array indexes. Capture `kind`, `label`, `srclang`, `default`, `mode`, `readyState`, absolute `src`, `track URL`, and exposed cue metadata only when available. Never enable a track or mutate playback.
3. Add discovered resource URL evidence from `<track src>`, media/source attributes, `performance.getEntriesByType('resource')`, and likely manifest/player resource URLs. Filter candidates using URL/content hints such as `vtt`, `webvtt`, `ttml`, `dfxp`, `srt`, `caption`, `subtitle`, `timedtext`, and provider-specific JSON markers, but label this as heuristic discovery, not proof.
4. Add provider/page data discovery as a bounded, conservative adapter. Inspect JSON script elements (`application/ld+json`, `__NEXT_DATA__`, `__INITIAL_STATE__`-style payloads), known player configuration objects only where safely enumerable, and caption-like URL/string keys. Parse JSON structurally; do not execute page strings or scrape arbitrary script text without a size cap. Record the exact field path and a redacted source reference.
5. Reuse `collectAccessibleDocuments`, `findAllVideos`, and `deepQuerySelector` conventions from `src/entries/content-script/index.ts` and `src/shared/utils/dom-query.ts` for same-origin documents/open shadow roots. Add explicit inaccessible reasons for cross-origin frames, closed shadow roots, opaque DRM/player internals, and canvas-only rendering.
6. Retain fallback evidence in the discovery model: native track with unavailable cues, caption-like DOM overlay/control, and optional opt-in DOM sampling. DOM sampling must be marked `source.kind = dom-sample`, timing as sampled/uncertain, and never presented as an exact downloadable caption source unless actual text/timing data was captured.
7. In `src/entries/content-script/index.ts`, add a handler adjacent to `GET_CAPTION_DIAGNOSTICS` that refreshes videos and returns discovery candidates. Preserve `GET_CAPTION_DIAGNOSTICS` during migration, implemented as an adapter/view over discovery where practical.

### Phase 3: Add service-worker retrieval and normalization
1. Add focused modules, likely `src/shared/utils/caption-fetch.ts` and `src/shared/utils/caption-normalize.ts`, with pure helpers for URL validation, format detection, bounded response reading, parser dispatch, and canonical document creation. Keep Chrome API calls in the service worker and pure parsing outside it.
2. In `src/entries/background/service-worker.ts`, add explicit cases for discovery forwarding and retrieval. The popup should identify the active `tabId`; the worker should request discovery from that tab, validate that the selected candidate was reported by that tab, then perform the fetch and parse. Do not let the worker fetch arbitrary popup-supplied URLs without provenance/allow-list checks.
3. Retrieval policy: permit only `http`/`https` candidates, reject `data:`, `blob:`, `file:`, `javascript:`, extension URLs, localhost/private-network targets unless explicitly needed, and unexpected redirects. Revalidate final URL and response origin. Limit request timeout, redirect count, response bytes, decompression risk, cue count, and per-cue text length. Avoid logging full URLs containing tokens.
4. Authentication policy: first try the discovered signed URL with `credentials: 'include'` where browser policy permits; report whether cookies/credentials were used or unavailable. Do not collect or persist cookies, bearer tokens, page secrets, or raw authorization headers. If the provider requires page-context auth/CORS, add an explicit content-script fetch fallback only when same-origin and permitted, otherwise return an actionable `auth/cors` uncertainty rather than bypassing protections. Do not add broad `webRequest` interception or DevTools protocol access in this phase.
5. Fetch raw bytes/text once, retain the exact bounded payload plus response headers needed for format/provenance, and pass a sanitized representation to the parser. Detect format from explicit provider metadata/content type/extension/magic markers, with deterministic fallback order: WebVTT, TTML/XML, SRT, provider JSON. Do not use a permissive parser that treats arbitrary HTML as captions.
6. Implement parsers for WebVTT, TTML/DFXP, SRT, and a provider-JSON adapter boundary. Preserve cue timing, plain text and structured spans, speaker/voice, language, cue settings, line/position/size/alignment, styles, regions, and parser warnings. TTML/XML parsing must use a safe non-executing parser and reject external entities/unsafe references; JSON must be treated as untrusted data with schema guards.
7. Normalize timing to finite seconds with `start < end`, retain original timestamp strings where useful for provenance, normalize overlapping/duplicate cues deterministically, and never invent exact times for DOM-sampled fallback. Assign field-level or cue-level confidence where values were inferred.
8. Add a derived-export utility for canonical JSON, WebVTT, SRT, and optionally TTML. Keep raw artifact and normalized artifact separate. Mark lossy exports, especially SRT styling/position loss and WebVTT/TTML feature loss.
9. Add or verify host permission behavior in `src/manifest.json`. Existing `<all_urls>` should cover normal HTTP(S) page resources, but document and test extension behavior on authenticated cross-origin resources, redirects, CSP, CORS, and private/local URLs before broadening permissions. Do not add `cookies` permission unless a separate product decision explicitly requires it.

### Phase 4: Replace popup probe UI with retrieval workflow
1. In `src/entries/popup/App.tsx`, replace or rename `probeCaptions`, `downloadCaptionDiagnostics`, and the current caption findings section with staged state: discovery loading/result, candidate selection, retrieval status per candidate, normalized result, raw artifact availability, and error/uncertainty details.
2. Route user actions through the new service-worker message contract so retrieval does not depend on popup-to-content-script direct access for network work. Keep the old diagnostic download available temporarily as a “diagnostic report” path if it helps migration/debugging.
3. Show source kind, language/label, URL host or redacted URL, confidence, provenance, timing certainty, auth/CORS/DRM limitations, and parser warnings. Never render caption text as HTML; use text nodes/React escaping, and avoid displaying full signed URLs.
4. Provide separate downloads through existing `chrome.downloads.download`: exact raw provider payload with a safe format/extension and normalized canonical JSON. Add derived WebVTT/SRT/TTML only when implemented and label them as exports. Handle data URL/blob size limits by using an extension-generated object URL or bounded data URL strategy appropriate to Chrome MV3; do not leave object URLs alive after download.
5. Add cancellation/duplicate-click protection and a response-size/progress state. The popup is ephemeral, so do not persist caption bodies or tokens in Zustand/sync storage. If long retrieval can outlive the popup, keep the worker operation bounded and make reopening rediscover/retrieve rather than relying on in-memory popup state.
6. Minimal migration boundary: leave playback controls, screenshot/audio capture, store state, and offscreen recording untouched. Remove the old diagnostic UI/types only after the new workflow has equivalent diagnostics and tests; otherwise retain a compatibility adapter until the replacement is stable.

### Phase 5: Tests, fixture coverage, and manual validation
1. Add `src/test/__tests__/caption-diagnostics.test.ts` updates or split into `caption-discovery.test.ts` for native track/source URL/provider-data/fallback evidence, same-origin iframe behavior, inaccessible cases, deduplication, redaction, and no DOM/playback mutation.
2. Add `src/test/__tests__/caption-normalize.test.ts` covering representative WebVTT, TTML with styles/speakers/regions, SRT, provider JSON variants, malformed input, overlap/duplicate handling, unsupported formats, timing warnings, and lossy export warnings. Assert raw payload is unchanged and canonical output is deterministic.
3. Extend `src/test/__tests__/content-script.test.ts` for the discovery message and `src/test/__tests__/service-worker.test.ts` for explicit discovery forwarding, candidate validation, retrieval success, timeout/size/auth failures, and response routing. Extend `src/test/fixtures/chrome.ts` with any missing downloads/fetch/runtime APIs rather than weakening types.
4. Extend `src/test/__tests__/popup.test.tsx` for discovery rendering, candidate selection, retrieval loading/error states, separate raw/normalized downloads, token redaction, and no-video/no-content-script behavior.
5. Add fixture endpoints and pages in `scripts/browser-fixture-server.mjs` plus `src/test/browser/caption-retrieval.spec.ts`: native WebVTT `<track>`, resource-timing candidate, provider JSON config, SRT/TTML responses, malformed response, redirect, oversized response, and an iframe/cross-origin limitation case. Use the existing `video-discovery.spec.ts` launch setup and build task.
6. Verification commands after implementation: `npm test -- --run`, `npm run type-check`, `npm run lint`, `npm run build`, and `npm run test:browser`. Run the browser fixture server/Chrome debug task for manual checks where the automated environment cannot model logged-in providers.
7. Manual validation in the debug Chrome profile: a simple HTML5/WebVTT page; a page whose caption URL is cross-origin but publicly fetchable; a logged-in provider with signed/authenticated caption URLs; a provider with captions embedded in JSON; a DRM/opaque player; disabled captions; seeking/reload behavior; and a page with cross-origin iframes. Confirm raw bytes and normalized cues match, downloads use safe filenames, no token is shown in UI/logs, and failures identify auth/CORS/DRM/format uncertainty without claiming success.

**Scope boundaries and decisions**
- Included: user-triggered discovery, candidate retrieval, raw payload preservation, canonical normalization, provenance/uncertainty, safe downloads, service-worker routing, and focused tests/fixtures.
- Excluded from the first implementation: request interception, `webRequest` body capture, DevTools protocol, cookie/token extraction, DRM decryption, audio transcription, bypassing CORS/authentication, persistent caption storage, and automatic background scraping.
- The canonical normalized download is versioned JSON because it preserves timing, text, spans, speakers, styles, language, source provenance, warnings, and uncertainty without forcing lossy WebVTT/TTML/SRT semantics. A derived WebVTT download is also offered as the standard convenience export; SRT/TTML remain later derived exports.
- Native/resource/provider candidates are preferred in that order for exact downloadable data. DOM sampling is an explicitly lower-confidence fallback and cannot manufacture exact cue timing.
- Raw provider data is preserved exactly within bounded limits and remains downloadable whenever safely fetched, even if normalization fails; normalized data is sanitized and deterministic. Signed URLs and secrets are redacted from displayed provenance and logs.
- Authenticated retrieval first uses a service-worker fetch with existing host permissions and reports auth/CORS failures clearly. Do not add cookie/token permissions in the first version.
- No settings/state persistence is needed for caption bodies in this iteration. The popup can rediscover/retrieve after reopening.

**Further considerations**
1. Confirm the intended authenticated-fetch policy before implementation: recommended Option A is extension-worker fetch with existing host permissions and explicit failure reporting; Option B is same-origin content-script fetch fallback; Option C is adding cookie/token permissions, which should be rejected unless a product requirement demands it.
2. Decide whether provider-specific JSON adapters are limited to a generic field-path heuristic in the first release or whether one named provider is supported. Recommended first release: generic adapters plus a small fixture provider, with provider-specific code added only from observed payloads.
3. Decide whether raw artifacts may be downloaded when normalization fails. Recommended yes: preserve the raw payload and report a separate normalization failure, provided size/security checks passed.
